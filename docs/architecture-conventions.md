# Architecture conventions

How a Homey app in this family is structured, and why. `AGENTS.md` has the short version. This document has the reasoning and examples.

These conventions come from what worked across the maintainer's apps (Philips TV, Home Connect, NS, App Insights for Developers) and from the official Homey docs. Where the apps disagreed, this document picks one way. Existing code that deviates can be migrated when you touch it. Don't start large rewrites just to conform.

---

## 1. Repository layout

```
.
├── .homeycompose/
│   ├── app.json                 # manifest source (the only place to edit app metadata)
│   ├── capabilities/<id>.json   # custom capabilities, one per file
│   ├── discovery/<id>.json      # mDNS-SD / SSDP / MAC strategies
│   ├── drivers/templates/       # optional shared driver fragments ("$extends")
│   └── flow/{triggers,conditions,actions}/<id>.json   # app-wide Flow cards
├── drivers/<driver_id>/
│   ├── driver.ts                # pairing, discovery, driver-level Flow cards
│   ├── device.ts                # thin: wires lib/ to the Homey Device API
│   ├── driver.compose.json
│   ├── driver.flow.compose.json # Flow cards bound to this driver's devices
│   ├── driver.settings.compose.json
│   ├── pair/*.html  repair/*.html
│   └── assets/{icon.svg, images/{small,large,xlarge}.png}
├── lib/                         # Homey-free code + shared base classes
│   ├── app-accessor.ts
│   ├── errors.ts
│   ├── <service>-client.ts
│   └── ...
├── widgets/<id>/                # optional
├── settings/index.html          # optional app settings page
├── locales/<lang>.json
├── assets/{icon.svg, images/}   # app icon and store images
├── tests/**/*.test.ts
├── scripts/                     # dev tooling (check-locales, generators); excluded from the build
├── docs/                        # contributor/agent docs (+ user docs if you use GitBook)
├── app.ts  api.ts
├── app.json                     # GENERATED by Homey Compose; gitignored, never hand-edited
├── README.md                    # GitHub readme (markdown allowed)
├── README.txt  README.<lang>.txt  # App Store long description (strict rules)
├── .homeychangelog.json
├── .homeyignore  .gitignore
├── env.example.json             # documents env.json keys; env.json itself is gitignored
├── AGENTS.md  CLAUDE.md  .homeyreview.md
├── tsconfig.json  tsconfig.test.json  eslint.config.mjs
└── package.json
```

### Why `app.json` is not committed

Homey Compose generates `app.json` from `.homeycompose/` and the driver compose files, and the docs say never to edit it by hand. These apps keep it out of git (`/app.json` in `.gitignore`):

- the compose files are the only source of truth, so nothing can drift;
- PRs show the real change instead of a large duplicated manifest, and parallel branches don't conflict on it;
- the CLI regenerates it on `run`, `build`, `validate`, `publish` and `review`, but refuses to start when no `app.json` exists at all. The `npm run homey-*` scripts seed it from `.homeycompose/app.json` first (`npm run homey-manifest`), and CI uses them.

This deviates from most Homey repos, which commit it. Consequences:

- after a fresh clone, run `npm run homey-build` (or any other `npm run homey-*` script) before reading `app.json` locally, and use the npm scripts rather than bare `homey app ...` commands;
- don't use `homey app version --commit` (it tries to stage `app.json`). Commit the version bump yourself;
- to see the full manifest, look at `.homeycompose/` and `drivers/*/driver.*.compose.json`, or build it locally.

### `lib/` and driver folders

- `lib/` holds everything that is not a direct Homey entry point: protocol clients, parsers, codecs, error classes, decision logic, and shared base classes for Driver and Device.
- `drivers/<id>/driver.ts` and `device.ts` stay thin. A `device.ts` over ~400 lines usually mixes concerns. Move the capability mapping, protocol handling or diffing into `lib/`.
- Domain code always goes in `lib/`, also in single-driver apps and also when only one driver uses it. A driver folder holds only `driver.ts`, `device.ts`, compose files, pair/repair views and assets.
- File names in `lib/` are kebab-case: `state-poller.ts`, `home-connect-client.ts`.

### Mark Homey-free code

A module that doesn't import `homey` can be unit tested without any SDK. Keep it that way. When such a module needs timers or logging, inject them:

```ts
// lib/timer-host.ts
export interface TimerHost {
  setTimeout(cb: () => void, ms: number): NodeJS.Timeout;
  clearTimeout(t: NodeJS.Timeout | undefined): void;
}
export type Log = (...args: unknown[]) => void;
```

In the device, pass `this.homey` as the `TimerHost` and `this.log.bind(this)` as the `Log`. In tests, pass a fake.

## 2. The App

The App is a small service container. It:

- creates shared clients and caches lazily (`this.client ??= new Client(...)`);
- owns `homey.settings` through typed accessors;
- registers app-wide Flow cards (via `lib/flow-controller.ts` when there are many);
- exposes methods that `api.ts` and widgets call.

```ts
// app.ts
import Homey from "homey";
import { SETTINGS } from "./lib/settings-keys";

class MyApp extends Homey.App {
  private pollTimer?: NodeJS.Timeout;

  async onInit(): Promise<void> {
    this.log("[app] init");
    this.homey.settings.on("set", (key: string) => this.onSettingChanged(key));
  }

  getApiKey(): string | null {
    return this.homey.settings.get(SETTINGS.API_KEY) ?? null;
  }

  async onUninit(): Promise<void> {
    this.homey.clearInterval(this.pollTimer);
  }
}

module.exports = MyApp;
```

### One typed accessor

Drivers, devices, `api.ts` and widgets reach the App through one function, so the cast happens in one place:

```ts
// lib/app-accessor.ts
import type Homey from "homey/lib/Homey";
import type MyApp from "../app";

export function getApp(homey: Homey): MyApp {
  return homey.app as unknown as MyApp;
}
```

If importing the App type creates a cycle, declare a narrow interface (`AppServices`) in `lib/` and have the App implement it.

## 3. Drivers and devices

### Lifecycle

| Hook | Use for |
| --- | --- |
| `Driver.onInit` | Cache Flow card handles, register driver-level run listeners. |
| `Driver.onPair(session)` / `onRepair(session, device)` | Pairing handlers (section 4). |
| `Device.onInit` | Migrations first, then listeners, then start connections or polling. |
| `Device.onAdded` | One-time work for a newly paired device (rarely needed). |
| `Device.onSettings({ oldSettings, newSettings, changedKeys })` | React to user changes. Throw a localized error to reject them. |
| `Device.onRenamed` | Rarely needed. |
| `Device.onUninit` | `teardown()`: app stops or updates. |
| `Device.onDeleted` | `teardown()`, plus cleanup of external registrations. |

`setSettings()` from code does **not** trigger `onSettings()`. If both paths need the same reaction, call the shared method yourself.

### Device `onInit` order

```ts
async onInit(): Promise<void> {
  await this.migrate();                  // 1. bring old devices to the current shape
  this.registerCapabilityListeners();    // 2. listeners before any value can change
  this.client = this.createClient();     // 3. build clients from store + settings
  this.startPolling();                   // 4. connections, polling, subscriptions
}
```

Don't block `onInit` on network calls that can hang. Start them and handle failure through availability.

### Thin subclasses over a shared base

When several drivers share behaviour (appliance types, device models), put it in `lib/base-driver.ts` / `lib/base-device.ts` and keep the driver classes tiny:

```ts
// drivers/oven/device.ts
import { ApplianceDevice } from "../../lib/appliance-device";
class OvenDevice extends ApplianceDevice {}
module.exports = OvenDevice;
```

Data-driven tables (`CAPABILITY_MAP`: feature → capability, decode, encode, trigger) beat a switch statement per capability, as long as the table and its codecs sit in their own module.

### Teardown

```ts
private stopped = false;
private generation = 0;

private teardown(): void {
  this.stopped = true;
  this.generation++;
  this.homey.clearTimeout(this.pollTimer);
  this.unsubscribe?.();
  this.client?.close();
}

async onUninit(): Promise<void> { this.teardown(); }
async onDeleted(): Promise<void> { this.teardown(); }
```

## 4. Pairing and repair

- Prefer **discovery** (`.homeycompose/discovery/` + `"discovery": "<id>"` on the driver) over manual IP entry. Homey then handles reachability and address changes, and reviewers push back on IP-only pairing. Keep manual IP as a fallback when discovery is known to be unreliable.
- Use system templates (`list_devices`, `add_devices`, `login_credentials`, `login_oauth2`, `pincode`, `loading`, `done`) where they fit. Custom views live in `pair/*.html` and use the Homey CSS classes (`homey-form-*`) and `Homey.__()`.
- Every view id passed to `session.showView(...)` or `Homey.showView(...)` must exist in `driver.compose.json`. Delete views that no flow reaches.
- Share handlers between `onPair` and `onRepair` with a per-session context object. Never keep pairing state on the Driver instance: two users can pair at once on Cloud, and two sessions can overlap on Pro.
- Guard handlers that hit the device against double submission (a single-flight helper).
- Report errors with localized messages (`session.emit("alert", this.homey.__("pair.error.x"))` or `throw new Error(this.homey.__(...))`). Make them diagnostic: "No dishwasher found. Found: oven, dryer" beats "No devices found".
- Device `data` gets an id that never changes (serial, MAC, cloud id). Never an IP or hostname.
- Offer a **repair** flow when credentials or connection details can change. It updates store and settings without breaking Flows. When repair changes both, write the store values before `setSettings`, because `setSettings` may trigger code that reads the store.
- Driver folder ids contain no spaces (spaces break custom pair views on Homey Pro 2016–2019). Display names may contain spaces and should not contain underscores.

## 5. Flow cards

### Where cards are defined

| Card type | Define in | Register listeners in |
| --- | --- | --- |
| Bound to one driver's devices | `drivers/<id>/driver.flow.compose.json` | that driver's `onInit` |
| Shared by several drivers (base class) | each driver's flow compose, ids prefixed (`oven_program_started`) | the base driver, through a helper that resolves `${prefix}_${card}` |
| App-wide (no device) | `.homeycompose/flow/...` | `lib/flow-controller.ts`, called from `App.onInit` |

Don't split one driver's cards between the App and the Driver. Card ids are unique across the whole app.

### Card content

- Short titles, no device names, no "When/And/Then", no parentheses. Use `titleFormatted` with `[[arg]]` for every card with arguments, and `!{{is|isn't}}` for conditions.
- Add a `hint` when the purpose isn't obvious from the title. Use `"highlight": true` on a few cards at most.
- Tokens get a localized `title` and an `example`.
- Argument autocomplete returns `{ name, description? }` objects, filters case-insensitively, and returns quickly (cache the list).

### Triggers

```ts
// Baseline: the first observation after a restart never fires.
if (this.previous === undefined) { this.previous = next; return; }
if (next !== this.previous) {
  this.changedTrigger
    .trigger(this, { value: next }, { previous: this.previous, value: next })
    .catch(this.error);
}
this.previous = next;
```

- Every `.trigger()` ends in `.catch(this.error)` or is awaited inside a try/catch.
- Put per-Flow conditions (thresholds, filters) in the trigger's `registerRunListener((args, state) => ...)`, so each Flow decides for itself.
- Use `card.getArgumentValues(device)` to skip expensive API calls when no Flow uses the card.
- Retire a card with `"deprecated": true`. Never rename or delete it.

### Actions

Actions throw on failure, with a localized message. Returning normally means success. If an action returns tokens (an advanced Flow card), declare them in compose.

## 6. Capabilities

- Use system capabilities when one fits. A custom capability is `.homeycompose/capabilities/<id>.json` with all supported languages, an `icon` under `assets/capabilities/`, and correct `getable`/`setable`/`uiComponent`.
- `setCapabilityValue` only for capabilities the device has. A safe helper (`hasCapability` check + `.catch(this.error)`) avoids crashes during migrations.
- Use `registerMultipleCapabilityListener` with a debounce for groups of buttons or values that change together.
- Capabilities that exist only for Insights (numeric shadow values) are fine. Set `preventTag` if they would clutter tokens.
- Probe-dependent capabilities (only some models support them) are added or removed from the probe result in `onInit`, guarded by `hasCapability`.
- The same goes for capabilities that depend on a transport or protocol setting: sync them in `onInit` and when that setting changes. Removing a capability that never had a value on that transport is safe; no Flow can use it.
- `setCapabilityOptions` is expensive. Only call it when the options actually changed.

## 7. Polling, connections and availability

### Polling loop

```ts
private schedulePoll(delayMs: number): void {
  const gen = this.generation;
  const jitter = delayMs * (Math.random() * 0.2 - 0.1);   // ±10%
  this.pollTimer = this.homey.setTimeout(() => {
    if (this.stopped || gen !== this.generation) return;
    this.poll()
      .catch((err) => this.error("[poller] poll failed", err))
      .finally(() => {
        if (!this.stopped && gen === this.generation) this.schedulePoll(this.intervalMs());
      });
  }, Math.max(1_000, delayMs + jitter));
}
```

- The generation counter makes a restarted loop (settings changed, reconnect) stop the old one, even when a poll is in flight.
- The interval comes from a driver setting when users have reasons to change it. Give min/max and a hint about rate limits.
- When several devices need the same remote data, poll once in the App or a shared client and fan out through an event feed (`lib/feed.ts` with subscribe/unsubscribe). Don't poll the same endpoint per device.
- A poll requested from outside the loop (a settings change, a reconnect) goes **through** the loop: run now when idle, otherwise right after the running poll. Never call `poll()` directly from `onSettings`; two overlapping polls write values and fire triggers in the wrong order. Keep the loop Homey-free (`lib/poll-loop.ts` with an injected `TimerHost`) so this is unit tested.
- One failed poll is often a network glitch. Act on N consecutive failures (two is usually enough) before writing "off" values, changing availability or firing triggers; otherwise users get stop/start trigger pairs in the middle of the day.
- Devices that switch off on a schedule (solar inverters at night, devices on a timer) are not "broken" when unreachable. Offer an offline behaviour setting, default to "treat as off" (keep available, write 0 / null), and keep lifetime totals untouched.
- Counters that the device only resets when it wakes up (energy today) are reset by the app at local midnight: compare the day of the last reading with today using `this.homey.clock.getTimezone()` and `Intl.DateTimeFormat`, never `Date#getDate()`.

### Long-lived connections

- Reconnect with exponential backoff plus jitter (for example 5 s → 10 s → … capped at 5 min), and reset after a stable connection.
- Ignore events from stale clients (generation guard).
- Wrap every socket and event handler body in try/catch. An exception in an event handler is an uncaught exception and crashes the app.

### Availability

| Situation | Call |
| --- | --- |
| Device unreachable, nothing works | `setUnavailable(this.homey.__("device.error.unreachable"))` |
| Missing credentials or configuration | `setUnavailable(this.homey.__("device.error.not_configured"))` |
| Partly working, data stale, or must stay controllable (Wake-on-LAN) | `setWarning(this.homey.__(...))` |
| Recovered | `setAvailable()` / `unsetWarning()` |

`setUnavailable` blocks all capabilities and Flow actions. Only change availability or warnings when the state changes, not on every poll. Keep last-known values when a refresh partly fails (`Promise.allSettled`).

## 8. Settings, store and data

| Kind | Scope | Who writes | Examples |
| --- | --- | --- | --- |
| `data` | device | pairing, immutable | serial, MAC, cloud id |
| `store` | device | the app | credentials, resolved host, probe flags, last-seen firmware |
| device settings | device | the user (and the app via `setSettings`) | IP override, poll interval, volume range |
| `homey.settings` | app | settings page + App accessors | API key, OAuth refresh token, account list |

- Key names are constants (`STORE.CREDENTIALS`, `SETTINGS.API_KEY`).
- Version keys whose shape may change (`widget_apps_v1`), so a migration can tell old from new.
- Secrets in app settings are never sent back to the settings page in full. Return a redacted form (`…1a2b`).

## 9. Migrations

Users update in place. Their devices, Flows and settings must keep working.

```ts
const ADDED_IN_1_4_0 = ["measure_power", "meter_power"];
const REMOVED_IN_1_4_0 = ["alarm_legacy"];

private async migrate(): Promise<void> {
  for (const cap of REMOVED_IN_1_4_0) {
    if (this.hasCapability(cap)) await this.removeCapability(cap).catch(this.error);
  }
  for (const cap of ADDED_IN_1_4_0) {
    if (!this.hasCapability(cap)) await this.addCapability(cap).catch(this.error);
  }
  if (this.getData().credentials && !this.getStoreValue(STORE.CREDENTIALS)) {
    await this.setStoreValue(STORE.CREDENTIALS, this.getData().credentials);
  }
}
```

Rules:

- Name migration lists after the version that introduced them. Run removals before additions.
- Adding a capability to the manifest does not add it to paired devices. That's what `addCapability` in `migrate()` is for.
- `removeCapability` deletes the Flow cards that use it and breaks users' Flows. Only use it for a capability that never worked or that the release notes call out as replaced. To retire a capability quietly, remove it from the manifest and keep its listener.
- Never change a device's `data`, a driver id, a capability id, a Flow card id or argument name, a setting key or the app id. Changing the app id means a new app: users must reinstall and rebuild every Flow.
- Change a device class with `setClass()` behind a guard.
- Add a test for every migration (old shape in, new shape out).

## 10. `api.ts`, settings page and widgets

### `api.ts`

- Thin: validate input, call an App method, return a plain object. No business logic.
- Typed: `({ homey, body, params, query }: { homey: Homey; ... })`, not `any`.
- Every endpoint is `"public": false` unless it really must be public. Not available on Homey Cloud.
- Long work returns `{ runId }` at once and streams progress:

```ts
homey.api.realtime("myapp:job:progress", { runId, step: "probing", pct: 40 });
homey.api.realtime("myapp:job:done", { runId, result });
homey.api.realtime("myapp:job:error", { runId, message: homey.__("settings.error.x") });
```

  The settings page subscribes once with `Homey.on(...)` and filters by `runId`. This avoids the settings-API request timeout. Events can arrive before the POST callback returned the `runId`: buffer them while a start is in flight and replay the matching ones, or a fast job ends in the page's watchdog.
- Return the result of `homey.api.realtime(...)` inside a promise chain (`.then(() => homey.api.realtime(...))`); it is typed `any`, and a rejection that isn't returned escapes the `.catch`.
- Messages returned to the UI are localized on the server (`homey.__`), or returned as locale keys that the page translates.
- Validate secrets server-side (`POST /test-api-key`). Browser `fetch` from the settings page hits CORS and leaks the key into page logs.

### Settings page

- `settings/index.html`, using Homey's CSS classes (`homey-form-group`, `homey-button-primary-full`, …) and `Homey.__()` / `data-i18n` for every string.
- Call `Homey.ready()` after the first render.
- Not available on Homey Cloud. A Cloud-capable app needs another way to configure (pairing, repair, device settings).

### Widgets

- `widgets/<id>/widget.compose.json`, `api.js`/`api.ts`, `public/{index.html,script.js,style.css}`, `preview-light.png`, `preview-dark.png`.
- The widget API is thin: it calls an App method and returns a compact, sanitized DTO (only the fields the widget renders, downsampled series).
- Use Homey CSS variables, escape every value you put into HTML, format with `Intl` for the user's language, and call `Homey.ready()` after the first render.
- Register widget setting autocomplete in the App: `this.homey.dashboards.getWidget(id).registerSettingAutocompleteListener(...)`.
- Previews: light and dark, 1024×1024, transparent, no screenshots or text (store rule).

## 11. Discovery

- Use Homey's strategies (mDNS-SD, SSDP, MAC) from `.homeycompose/discovery/`. Don't build your own broadcast or subnet scan next to them, even when a vendor tool does: it duplicates what Homey already does and is harder to review.
- Normally link the strategy from `driver.compose.json` so Homey manages reachability, and implement `onDiscoveryResult` (match by stable id), `onDiscoveryAvailable` (connect), `onDiscoveryAddressChanged` (update settings or store, reconnect) and `onDiscoveryLastSeenChanged` where useful.
- **Exception:** a linked strategy makes Homey manage availability. For devices that are routinely offline but must stay available (a solar inverter at night), read the strategy unlinked, the way Athom's own apps do: `this.homey.discovery.getStrategy(id)`, walk `getDiscoveryResults()`, listen to `strategy.on("result")` and `result.on("addressChanged")`. Explain the choice in `.homeyreview.md`.
- **MAC strategy** for devices without mDNS or SSDP: prefixes are decimal byte arrays (`AC:CF:23` → `[172, 207, 35]`). Chip vendors share prefixes with many other products, so a result is a candidate that pairing still probes. The MAC is the result id; `data.id` usually isn't, so keep the device's MAC in the store (from the discovery result or `homey.arp.getMAC(ip)` with a timeout at pairing, learned after a successful poll for older devices) and match on that.
- Prefer IPv4 when a device advertises both and the protocol is known to misbehave on IPv6.
- Discovery is not available on Homey Cloud.

## 12. Documentation in the repo

| File | Audience | Rules |
| --- | --- | --- |
| `README.txt`, `README.<lang>.txt` | App Store users | plain text, 1–2 paragraphs, no features/URLs/markdown (see `docs/app-store-guidelines.md`) |
| `README.md` | GitHub visitors | what it is, store link, supported devices, development commands, link to the community topic |
| `docs/` user pages (optional, GitBook) | users | features, FAQ, troubleshooting. Keep the changelog page in sync, or link to the store instead of duplicating it. |
| `docs/*.md` conventions | contributors and agents | this set |
| `CONTRIBUTING.md` | contributors | project-specific: how to run, test, open a PR. Not Athom's boilerplate. |
| `DIAGNOSE.md` / troubleshooting | users | how to send a diagnostic report and where to post the Log ID |

Design notes about a quirky device or protocol (why polling can't be replaced, why requests are serialized) belong in `docs/development/<topic>.md`. Code comments link to them.
